### The sweeps added in P1-6

All three are generated from the running application, so a new route is covered the day it exists.

1. **Cross-business sweep** (`test/integration/idor-sweep.spec.ts`, 52 tests). Business A owns real records of every kind (product, supplier, purchase, supplier return, transfer, batch, role, team member, session). Business B's owner, fully trusted inside B, then tries **every route that has an id in its address (31 of them)** and **16 more cases where A's id is only referred to inside a form or filter**. The rule: it answers 404 as if the record did not exist (or a refusal in a form), nothing about A appears in what B was told, and A's data is byte-for-byte unchanged afterwards. A completeness test lists every route with an id in its address from the app and fails if one has no probe. Also checked: the same Idempotency-Key used by two businesses never replays the other's answer; a person limited to one branch is refused (403) on every branch-bound route for the other branch.
2. **Route-by-role table** (`test/integration/role-route-matrix.spec.ts`, 3 tests, output `docs/api/permission-matrix.md`). For all 91 routes: who may call it as Owner (91), Admin (91, after the owner gave Admin the team and settings rights in the review) and Cashier (33). The committed table must match the code, and a cashier by default can call no route that needs cost, writing, stock changes, audit, team or settings. This sits on top of the request-level matrix from P1-2, which calls every route as five different people and checks the exact answer, including the audit entry for each refusal.
3. **Cashier leak sweep** (`test/integration/cashier-leak-sweep.spec.ts`, 2 tests). Calls every read route a cashier may reach, with real records that have a real cost behind them, and fails on any field name that reveals cost, margin, profit or landed cost, or on the secret cost value anywhere in the body. A control proves the scan can find cost (the owner's answer has it). Checked by sabotage: making the cost check always say yes made the sweep fail on `/v1/products`, `/v1/products/{id}`, by-barcode and `/v1/stock`.

## 3. Performance numbers

Measured on a developer laptop (Windows 11, PostgreSQL and Redis in Docker, API built with `nest build`, one signed-in owner, requests one after another, 20 to 30 repeats). Data: the demo set from `pnpm db:seed:shops` (3 businesses, 600 products, 72 purchase bills, 1,296 ledger rows). These are **local numbers, not a load test**; they show nothing is slow by accident.

| Call                                                       | p50   | p95   |
| ---------------------------------------------------------- | ----- | ----- |
| `GET /v1/products?limit=50`                                | 18 ms | 22 ms |
| `GET /v1/products?limit=200`                               | 24 ms | 32 ms |
| `GET /v1/products?q=whey`                                  | 18 ms | 22 ms |
| `GET /v1/products/by-barcode/{barcode}` (the scanner path) | 13 ms | 16 ms |
| `GET /v1/stock?branchId` (50 rows)                         | 20 ms | 23 ms |
| `GET /v1/stock/ledger` (one product)                       | 17 ms | 21 ms |
| `GET /v1/stock/alerts`                                     | 20 ms | 23 ms |
| `GET /v1/purchases`                                        | 14 ms | 18 ms |
| `GET /v1/audit?limit=50`                                   | 21 ms | 30 ms |
| `POST /v1/purchases` (3 lines)                             | 57 ms | 88 ms |
| `POST /v1/stock/adjustments` (a count)                     | 29 ms | 69 ms |
| `GET /v1/stock/verify`                                     | 29 ms | 31 ms |
| `GET /v1/audit/verify` (about 290 entries)                 | 45 ms | 63 ms |

The till's budget (a scanned item on the screen in well under 100 ms of server time) is met with room to spare for the lookup path. **Audit verify at scale:** with 100,000 audit entries a first call (which seals the backlog, 200 batches) took 26 s and a repeat call 9 s. That is fine for a rare owner action today but is why verification should move to a background job (open item D-2).

Performance fix made in P1-6: audit sealing and verification did one database query per entry; they now read and write in batches, 10 times faster (441 ms to 45 ms at 290 entries).

## 5. What these tests do not prove

- **Agent reviews and dependency audit (run 20 Oct 2026, after P1-6).** The `reviewer` found no S1, one S2 and several S3/S4; the `security-auditor` found no S1, the same S2 and one S3. Everything marked fixed in section 4 was fixed and tested. The agents read the code; they did not run it, so their clean checks are opinions, not proof. `pnpm audit`: web has no known production vulnerabilities (one high in a dev-only linter dependency, `braces`); backend has three (see D-16).
- **Sweeps find what they probe.** The cross-business sweep covers ids in addresses, bodies and filters for the routes that exist today; it cannot catch a leak through a response field that is not an id, or through timing. Row-level security in the database is the second wall and has its own tests on every tenant table (the RLS coverage test fails when a tenant table lacks it).
- **No load or soak test.** Numbers above are single-user. Concurrency is tested for correctness (last-unit race, simultaneous idempotent POSTs, simultaneous sealing), not for throughput.
- **No penetration test.**
- **Web is tested against a pretend API.** The live runs for P1-1 to P1-5 covered the real stack; P1-6 changed no web code.

## 6. Risks for Phase 2 (the till)

1. **Money rules meet real invoices for the first time.** GST rate slabs (0, 0.25, 3, 5, 18, 40%) and the HSN suggestions are still unconfirmed by a CA; invoice number format and rounding rules must be settled before the first real bill (Phase 2 plan has the CA review).
2. **Negative stock.** The ledger refuses it today. A shop that sells before it records a purchase will hit `INSUFFICIENT_STOCK` at the till. A shop-level policy ("allow negative, flag it") needs the owner's decision before P2.
3. **Offline.** The till's offline queue and sync are the largest unknown; the idempotency design (a key per bill) is ready for it, nothing else is.
4. **Audit and idempotency growth.** Both tables grow with every action; clean-up and anchoring wait on the job runner (D-2, D-5).
5. **Single Redis, single API instance** in the design so far. Fine for a pilot, to be revisited with the deployment work that the owner deferred.
6. **Reviews done, but only by reading code** (section 5); no penetration test.

## 7. Recommendation

Phase 1 meets its definition of done on the evidence above: every story is implemented end to end, no S1/S2 is open, tests are green, and the protections that matter most (business walls, permissions, cost secrecy, immutability, idempotency) are each checked by generated tests as well as by hand-written ones. **The agents and `pnpm audit` have now run, and every S2/S3 finding they raised was fixed or recorded above. The open questions that blocked Phase 2 were answered (see `docs/07-open-questions.md`). Before the till: build the web team screens and the QR code for two-step setup, as decided.**
