# ADR 002: Tenant isolation with PostgreSQL row-level security and Prisma

- Status: Accepted (16 Oct 2026, implemented in P0-2)
- Deciders: Owner, architect agent
- Related: `docs/03-engineering/architecture.md` §4, `docs/03-engineering/security.md`, user story US-SEC-01/02

## 1. Context

Dumbbill hosts many retail businesses ("tenants") in one database. The most important promise of the product is that **one business can never see or change another business's data**, even if a developer makes a mistake (a forgotten filter, a copy-pasted query, a guessed id in a URL).

Relying only on `WHERE tenant_id = ?` in application code is fragile: one missed filter in one query is a data leak. We want the **database itself** to enforce the rule as a second, independent layer.

## 2. Decision

1. **Shared database, shared tables, a `tenant_id` column on every tenant table**, protected by PostgreSQL **row-level security (RLS)**.
2. **Two database roles**
   - **owner** (`DATABASE_URL`): creates tables, runs migrations and seeds. Used by tooling only.
   - **app role `dumbbill_app`** (`APP_DATABASE_URL`): used by the running API. `NOSUPERUSER`, `NOBYPASSRLS`, no `CREATE`, no access to Prisma's `_prisma_migrations`. Created and refreshed by `scripts/setup-db-roles.mjs` (`pnpm db:roles`, run automatically by `db:migrate` and `db:deploy`).
3. **Every request runs inside a transaction that first says which business it is for:** `SELECT set_config('app.tenant_id', $1, true), set_config('app.user_id', $2, true)`. The third argument `true` makes the setting **transaction-local**, so it disappears at commit/rollback and can never leak to the next request on a pooled connection.
4. **One standard policy on every tenant table**, installed by the SQL function `enable_tenant_rls('<table>')`:
   - `ENABLE` and `FORCE` row-level security (FORCE so the table owner is also bound),
   - policy `tenant_isolation` for `ALL` commands: `USING` and `WITH CHECK` both `tenant_id = (SELECT app_current_tenant_id())`.
5. **Fail closed.** `app_current_tenant_id()` returns `NULL` when nothing was set; `NULL` equals nothing, so a query with no tenant sees zero rows and cannot write.
6. **Application API:** business code injects `TenantTx` and calls `tenantTx.run(tx => ...)` (tenant taken from the request context, an `AsyncLocalStorage`) or `tenantTx.runAs({tenantId}, tx => ...)` (jobs, webhooks, tests). Business code must not use `PrismaService` directly; an ESLint rule enforces it.
7. **Ids:** tenant tables use UUIDv7 (time-ordered, generated by Prisma with `@default(uuid(7))`). Tiny global reference tables keep the database default.
8. **A generated audit test** (`test/security/rls-coverage.spec.ts` using `test/support/rls-audit.ts`) inspects the real database catalog and fails if any table is neither on the explicit `GLOBAL_TABLES` list nor fully protected (column, RLS enabled and forced, policy with `USING` and `WITH CHECK`, app role has access).

## 3. How it fits together

```
HTTP request
  -> (P1-1) auth guard verifies the token, fills TenantContext {tenantId, userId}
  -> service calls tenantTx.run(tx => ...)
       BEGIN
       SELECT set_config('app.tenant_id', '<uuid>', true) ...
       ...queries, with RLS hiding every other business...
       COMMIT   (settings vanish)
```

Special cases (decided now, built when needed):
- **Signup** creates the tenant and its first owner. It generates the tenant id first, runs with that id as the context, and inserts the `tenants` row (allowed because `id` equals the context) and the `users` row in the same transaction.
- **Login by email** must find a user before knowing the tenant. This uses a narrow `SECURITY DEFINER` database function (`find_login_by_email`) that returns only the fields login needs, so the app role never gets a general "see every tenant" ability. **Built in P1-1.** Because tables use FORCE row-level security, the function is owned by a dedicated role `dumbbill_auth` that has its own SELECT-only policy and column grants (see ADR 006 section 6); a function owned by the normal owner would find no rows in production.
- **Append-only tables:** `app_grant_defaults()` now removes UPDATE/DELETE/TRUNCATE again for every table on its `append_only` list (currently `audit_log`). **Add new append-only tables (stock_ledger, points_ledger, ...) to that list** in the migration that creates them; otherwise the next migration's grants would reopen them.
- **Super Admin** actions across tenants use a separate, audited code path and role (Phase 4), never the normal app role.
- **Reference tables** (`plans`, `gst_states`, `category_templates`) are global: no `tenant_id`, no RLS, readable by the app role.

## 4. Adding a new tenant table (checklist)

1. In `schema.prisma`: add `tenantId String @map("tenant_id") @db.Uuid`, an index starting with `tenant_id`, and `@default(uuid(7))` on the id.
2. `pnpm db:migrate --name add_<thing>`; open the new migration and **append**:
   ```sql
   SELECT enable_tenant_rls('<table>');
   SELECT app_grant_defaults();
   ```
   (For append-only tables such as `audit_log`, also `REVOKE UPDATE, DELETE ON <table> FROM dumbbill_app;`.)
3. Run `pnpm test:sec`. The audit fails with a message naming the table and what is missing.
4. Never use `PrismaService` in the new module; use `TenantTx`.

## 5. Consequences

Good:
- A forgotten filter cannot leak data; it returns nothing.
- A request cannot write into another business, even by inserting a different `tenant_id` or moving a row.
- New tables cannot slip in unprotected: the audit test fails.
- The security property is tested against a real PostgreSQL, including connection reuse and concurrency.

Costs and caveats (be aware):
- **Every database access needs a transaction** so the setting is applied. The overhead is small (one extra statement) but real. Long transactions hold a connection; `TenantTx` sets `maxWait` 5 s and `timeout` 15 s.
- **Do not run request queries on `PrismaService` directly**: they have no tenant and will see nothing. This is the safe failure mode, and the lint rule makes it obvious.
- **Connection pooling:** safe with PgBouncer in transaction mode because only transaction-local settings are used. Never use plain `SET` or session-level `set_config(..., false)`.
- **Development uses a superuser owner** (the Docker `dumbbill` user). Superusers bypass RLS completely, which is why the API and the tests connect as `dumbbill_app`. In production, make the owner a normal (non-superuser) role. Seeds and one-off scripts that touch tenant tables as the owner must also set the tenant (`FORCE` binds a non-superuser owner).
- **Foreign-key checks bypass RLS** (PostgreSQL runs them with the owner's rights). Application code must still ensure it only references rows of its own tenant; composite foreign keys (`tenant_id, id`) can be added on sensitive relations later.
- **Unique constraints are global** (for example `users.email`). A duplicate in another business is therefore detectable by an error message; this is deliberate for emails (one email, one account) but must be considered for each new unique column (prefer unique indexes that include `tenant_id`).
- **Prisma and raw SQL:** `tx.$queryRaw` runs inside the same transaction, so it is protected the same way.
- **Grants after a database reset:** default privileges are lost when a database is reset, which is why every migration calls `app_grant_defaults()` explicitly.
- **Test strategy deviation:** the plan said Testcontainers. Tests instead use the PostgreSQL from `docker compose` and create a **throwaway database per test file** (real role script, real migrations, dropped afterwards). It is faster, has no extra image to pull, and your development data is never touched. If CI is added later, run a `postgres:16` service container with the same `TEST_ADMIN_DATABASE_URL`.

## 6. Alternatives considered

| Option | Why not |
|---|---|
| `tenant_id` filter in application code only | One missed filter leaks data. Kept as the first layer, but not the only one. |
| Schema per tenant | Migrations multiply with every tenant; hard to operate at hundreds of tenants. |
| Database per tenant | Strongest isolation but expensive and heavy to operate; only worth it for very large enterprise customers. |
| Prisma client extension that adds `where tenant_id` | Still application-level; raw queries bypass it. Could be added later for convenience, not as the guarantee. |
| Drizzle ORM | Considered for explicit SQL control, but the owner chose Prisma; `$transaction` + `set_config` gives the same guarantee. |

## 7. How we know it works

- `test/integration/tenant-isolation.spec.ts` (20 checks): unfiltered queries see only their own business; cross-tenant update, delete, insert and row-moving are refused; no tenant set means no rows; the setting never leaks over reused connections; 30 simultaneous requests for two businesses stay separate; failed work rolls back; invalid tenant ids are rejected.
- Sabotage check done once during P0-2: with RLS switched off on `users`, 12 of the 20 isolation checks failed, proving the tests detect a leak.
- `test/security/rls-coverage.spec.ts`: the clean schema passes; removing a policy, forcing off, disabling RLS, dropping `WITH CHECK`, adding an unprotected tenant table, adding a table with no tenant column, and forgetting grants are each detected.
- `test/unit/lint-rules.spec.ts`: the lint rule that bans `PrismaService` in business code fires where it should and stays quiet where it is allowed.
