# ADR 008: How invoice PDFs are produced

- Status: **Provisional** (17 Oct 2026). Confirmed or changed by a short spike at the start of P2-4, and then recorded here.
- Deciders: Owner, architect agent
- Related: `docs/03-engineering/architecture.md` §10, §11, US-POS-05, `docs/runbooks/file-storage.md`

## 1. Context

Dumbbill needs PDFs for: GST invoices and bills of supply (A4 and 58/80 mm thermal width), credit notes, the shop QR poster, and some report exports. Needs:
- **Correct and repeatable.** A reprinted invoice must look identical; it is a legal document.
- **The rupee sign must render.** Only Inter Tight has ₹ in our font set (see design-system runbook).
- **Cheap to run.** The first production target is one small server at about US$150/month in total.
- **Not on the checkout path.** Checkout stores the invoice first; the PDF is made afterwards by a background job (BullMQ), so a slow PDF never delays a sale.

The architecture note listed two candidates: a headless browser (Playwright/Chromium) or `@react-pdf`.

## 2. Decision

1. **Use a plain Node PDF library, not a browser.** Recommended: **pdfmake** (built on PDFKit). It describes a document as data, runs inside the Node worker with no browser, and embeds TrueType fonts. Layouts are built from the already-validated invoice data with fixed rules, not from HTML.
2. **Fonts:** embed Inter Tight (for ₹ and body), Barlow Condensed (headings) and JetBrains Mono (codes). The TTF files already exist from the mobile work (`dumbbill-mobile/assets/fonts/`); the backend gets its own copy through a script, so no code is shared across apps.
3. **Layouts:** one template function per page type: `A4 invoice`, `58 mm receipt`, `80 mm receipt`, `credit note`, `QR poster`. Thermal page widths are custom page sizes with a continuous height.
4. **PDFs are generated by the worker** after the invoice is final, saved through the `FileStorage` interface (`invoices/<uuid>.pdf`), and served only through authenticated routes or the signed public invoice link (US-POS-05). Reprints reuse the stored file and are audited.
5. **A PDF is a rendering of immutable data.** If the template changes later, old PDFs are not silently regenerated; a reprint after a template change is generated on demand and labelled as a reprint.
6. **Testing:** golden-file tests compare the extracted text and layout positions (not raw bytes) for a fixed set of invoices, including a very long product name, Indian digit grouping, inter-state and intra-state tax, and the ₹ sign.
7. **Spike gate (start of P2-4), one hour of work:** render one invoice in pdfmake at A4 and 58 mm with the embedded fonts and confirm: the ₹ renders in prices, text wraps correctly for long names, and memory stays small. If it fails, fall back to headless Chromium running as a **separate worker process** with a strict memory limit, and update this ADR.

## 3. Consequences

Good:
- Small memory use and fast start; fits the small server.
- No browser to patch, sandbox or keep alive; fewer security surfaces.
- Deterministic output from data, which suits golden-file review by the chartered accountant.

Costs and caveats:
- Layouts are written in the library's document format instead of familiar HTML/CSS, so complex designs take more effort.
- Thermal **printing at the till** is separate and uses ESC/POS or browser print CSS (P2-4); this ADR covers the downloadable/shareable PDF only.
- If much richer branded layouts are needed later (for example marketing PDFs), a browser renderer may become worth its cost then.
- Right-to-left or complex Indic scripts are not supported; invoices are English only (decided).

## 4. Alternatives considered

| Option | Why not (or when it wins) |
|---|---|
| Playwright / headless Chromium | Pixel-perfect HTML and CSS reuse, but needs roughly several hundred MB of memory, slow cold starts, a bigger container and regular security updates. Kept as the fallback if the spike fails. |
| `@react-pdf/renderer` | Works without a browser, but pulls React into a backend that otherwise has none. Not chosen unless the spike favours it. |
| A third-party PDF API service | Sends invoice data to another company and adds a per-document cost; avoided for privacy and cost. |
| Generating PDFs in the browser | Cannot be trusted as the legal copy, and mobile and WhatsApp links need a server file anyway. |
